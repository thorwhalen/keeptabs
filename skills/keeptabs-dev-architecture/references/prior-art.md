# Prior art for an AI-centric technology-watch (veille) package

Research date: 2026-09-27. Scope: (1) existing watch, monitoring and radar tools; (2) open-source LLM-based digest and research agents; (3) methodology literature (horizon scanning, competitive/technology intelligence, weak signals, French *veille*, intelligence cycle, source grading, maturity models). Maintenance status comes from each repository's last push date as shown by the GitHub API on the research date.

## Key takeaways

- Nobody ships the whole loop we want (declarative subject spec, then acquisition, entity matching, entity records, question answering, digest) as a library. The pieces exist separately: feed plumbing (`reader`, Miniflux, FreshRSS), change detection (changedetection.io), event graphs (Huginn), radar visualisation (BYOR, Zalando), preference learning (arxiv-sanity-lite, Scholar Inbox, NewsBlur), and LLM report writing (GPT Researcher, STORM).
- The commercial leaders (Feedly AI, Inoreader, Owler) converge on the same four primitives: a tracked-concept model that is more than keywords, rules/filters with actions, deduplication, and mute/feedback. Those are the primitives the package's spec format should express.
- The methodology literature is consistent on three points the package should encode from day one: every observation is graded for source reliability and information credibility separately (Admiralty code); a signal is not an interpretation (Hiltunen); and scanning is only the first stage of a cycle that must close with feedback (intelligence cycle, Cuhls).

## 1. Existing tools and frameworks

### 1.1 Commercial intelligence readers

**Feedly** has moved from RSS reader to "Feedly AI", a set of machine-learning models that "gather, analyze, and prioritize information" from millions of sources, with vertical model families for threat intelligence (vulnerabilities, malware families, threat actors, MITRE ATT&CK), market intelligence, risk intelligence and biopharma research [1]. The AI assistant was originally branded Leo and shipped to individuals through the Pro+ plan [2]. The key design idea is the *AI Model*: a trained concept ("Leadership Changes", "Funding Events", "Product Launches") that goes beyond keyword matching, and which users combine into *AI Feeds* [3]. Feedly also markets deduplication of repetitive news and muting of irrelevant topics as first-class features [4]. **Borrow:** concepts-as-classifiers (a tracked "business event" type is a reusable predicate, not a query string), and mute as explicit negative feedback.

**Inoreader** exposes *rules* (condition, then action: tag, save, notify, export to email or storage) and two kinds of *filters*: content filters (keep or drop on title, content, author, URL) and duplicate filters [5]. Since January 2024 its "monitored keywords" became *monitoring feeds*, which search the web for matches in sources the user does not subscribe to, and which can be combined into folder-level email digests [6]. **Borrow:** the split between a subscribed-source feed and a query-defined monitoring feed; declarative condition/action rules; digests defined per folder (per subject area).

### 1.2 Self-hosted readers, monitors and automation

**Huginn** (MIT, about 50k stars, pushed 2026-09-26) lets users build *agents* that create and consume *events* along a directed graph, packaged as shareable *scenarios*; it describes itself as a hackable, self-hosted IFTTT or Zapier [7]. **Borrow:** the event graph as the core abstraction (acquire, filter, enrich, notify are all agents emitting events), and exportable scenarios as the unit of sharing, which maps well onto our spec files.

**changedetection.io** (Apache-2.0, about 34.6k stars, pushed 2026-09-25) watches arbitrary pages and narrows them with XPath, CSS, JSONPath or jq, fires on text or regex triggers and conditions (for example price thresholds), notifies through more than 100 channels via Apprise, and now offers plain-language LLM change rules and change summaries with OpenAI, Gemini, Anthropic or Ollama backends [8]. **Borrow:** a "page watch" source type for sites without feeds; a selector plus trigger model; Apprise as the notification seam.

**FreshRSS** (AGPL-3.0, about 16.2k stars, pushed 2026-09-26) supports advanced filters and custom tags, full-text search, Google Reader and Fever APIs, WebSub push, and XPath/JSON scraping of sites without feeds [9]. **Miniflux** (Apache-2.0, about 9.7k stars, pushed 2026-09-23) is a single Go binary on PostgreSQL with a REST API that has a Python client, scraper and rewrite rules, and 25+ integrations [10]. **Tiny Tiny RSS** lost its original infrastructure on 1 November 2025 when its author shut down tt-rss.org; a long-time contributor's fork continues on GitHub and the domain now redirects there [11]; that repository (GPL-3.0) was pushed 2026-09-25 [12]. **NewsBlur** (MIT, pushed 2026-09-24) has a *training* feature ("hide the stories you don't like and highlight the stories you do") and now ships an MCP server with a `newsblur_train_classifier` tool that trains like/dislike on title, author, tag or feed [13]. **Borrow:** WebSub for push, the XPath-scrape-to-feed trick, and NewsBlur's per-facet like/dislike training as a lightweight, explainable feedback model. The TT-RSS episode is also a reminder that a user's archive should never depend on one project's hosting.

**`reader`** (BSD-3-Clause, 558 stars, pushed 2026-09-26) is the closest Python prior art at the library level: a feed-reader *library* with no framework dependency, persistent storage, plugins, full-text search, arbitrary tags on feeds and entries, batch updates, feed discovery and OPML import/export [14]. **Borrow or depend on:** it is a credible default for the RSS/Atom/JSON Feed acquisition seam, and its "tags on anything" metadata model is a good fit for a key-value store.

### 1.3 Technology radars

The **Thoughtworks Technology Radar** is published twice a year; the latest is Volume 34 (April 2026) [15]. Its four rings are now **Adopt, Trial, Assess and Caution**; the outer ring formerly called Hold is now defined as "the industry should consider alternative options or even proactively avoid these things" [15]. Blips are nominated by practitioners from project experience, debated, and voted in by a Technology Advisory Board; a blip that does not move fades from the radar after one edition unless there is something new to say [16]. Quadrants categorise blips as Techniques, Tools, Platforms, and Languages & Frameworks [16]. **Build Your Own Radar** (AGPL-3.0, pushed 2026-04-22) renders a radar from a sheet, CSV or JSON with columns `name, ring, quadrant, isNew, description` and an optional `status` of New, Moved In, Moved Out or No Change [17]. **Zalando's tech-radar** (MIT, pushed 2026-09-17) takes entries with `label, quadrant, ring, moved`, where `moved` is -1 (out), 0 (unchanged), 1 (in) or 2 (new) [18]. **AOE's technology radar** is a static-site generator for radars kept as files (pushed 2026-09-25) [19]. **Borrow:** ring plus movement as the entity's human-assigned status; the fade rule (silence is information); and a BYOR/Zalando-compatible export so a subject area's entities can be viewed as a radar with no new UI.

### 1.4 Event, mention and entity monitoring

**GDELT** monitors world news in 65 machine-translated languages; its DOC 2.0 API does full-text search over a rolling three-month window and returns article lists, volume timelines (as a share of all monitored coverage), tone timelines and image collages [20]. GDELT 2.0 updates its Event, Mentions and Global Knowledge Graph tables every 15 minutes; the GKG extracts people, organisations, locations, themes and emotions from each article [21]. A maintained MIT Python client, `gdeltdoc`, exists [22]. **Borrow:** GDELT as a free "global news" source adapter, and the normalised-volume timeline as a ready-made trend signal.

**Google Alerts** offers "as-it-happens", daily or weekly delivery over source types (news, blogs, web, video, books, discussions, finance), and RSS delivery was restored after Google Reader's demise [23], [24]. **Talkwalker Alerts** is a free alternative that adds Boolean queries and covers news, blogs, forums and Twitter [25]. **Mention** and **Brand24** are paid social-listening tools whose differentiators are sentiment analysis, influencer scoring and crisis alerts [26]. **Owler** tracks more than 20 million companies and emails an instant alert when any of fifteen trigger events (funding, acquisition, leadership change and so on) happens to a followed company, plus a personalised daily snapshot built from the user's competitor graph [27]. **Borrow:** Google/Talkwalker alert RSS as cheap zero-code sources; Owler's typed trigger-event list as the vocabulary of entity updates; and "follow an entity" as the core user gesture.

### 1.5 Research-literature watch

**Zotero** subscribes to RSS feeds (arXiv included), with per-feed update frequency and retention settings and OPML import [28]. **Semantic Scholar** turns each library folder into a *Research Feed* using a contrastively trained paper-embedding model, with email alerts, plus alerts on new citations and on followed authors [29]. **arxiv-sanity-lite** (MIT, last push 2023-06-19, effectively dormant) lets users tag papers and recommends similar ones per tag using SVMs over TF-IDF of abstracts, with daily emails and SQLite storage [30]. **Scholar Inbox** (2025) trains a per-user recommender on up/down ratings, uses a map of science to solve cold start, actively asks users to rate papers, and indexes arXiv, bioRxiv, medRxiv, ChemRxiv and open CS proceedings daily [31]. **alphaXiv** layers discussion, trending papers and author following on top of arXiv [32]. **Hugging Face Daily Papers** is a curated and community-submitted feed with upvotes and a JSON API per paper [33]. **Borrow:** a *tagged exemplar set* per tracked subject (positive examples defining the subject better than keywords do), active-learning prompts for ratings, and community signals (upvotes, discussion counts) as relevance features.

## 2. Open-source LLM-based digest and research agents

Two families exist: *deep-research agents* that answer one question on demand, and *digest pipelines* that run on a schedule. Neither keeps persistent entity records; both regenerate from scratch each time.

**Deep-research agents.** **GPT Researcher** (Apache-2.0, about 29.6k stars, pushed 2026-09-26) splits work into a planner that generates research questions, execution agents that gather sources (it "aggregates over 20 sources"), and a publisher that writes a cited report; it supports MCP sources and a recursive "deep research" mode with configurable depth and breadth [34]. **STORM** (MIT, about 31.5k stars, last push 2025-09-30) writes Wikipedia-style cited articles through a pre-writing stage of *perspective-guided question asking* and simulated writer-expert conversations, then an outline, then the article; Co-STORM adds a moderator and a shared mind map for human-in-the-loop steering [35]. LangChain's **open_deep_research** (MIT, about 12.7k stars) is now archived, as is **crewAI-examples** (about 6.2k stars), which held the frequently copied crewAI newsletter examples [36], [37]. **Borrow:** the planner/executor/publisher split for the "what's new about X" answer path; STORM's perspectives as a way to widen a subject spec's queries; and citations as a hard requirement of every generated claim.

**Digest pipelines.** **AINews** (news.smol.ai) is the best-known production example: a daily roundup that summarises top AI Discords, subreddits and X accounts, formerly on Buttondown and now self-hosted [38]; its site repository is public but unlicensed [39]. **auto-news** (MIT, about 900 stars, last push 2025-07) pulls RSS, Reddit, tweets, YouTube and web articles, uses LLMs through LangChain to filter out what it calls "80%+ noises", and writes to Notion, with weekly recaps and TODO extraction [40]. **Folo** (AGPL-3.0, about 39k stars, pushed 2026-09-27) is an actively developed "AI RSS reader" [41]. **RSS-GPT** (MIT, about 360 stars, last push 2025-09) summarises personal RSS feeds with ChatGPT, run from GitHub Actions [42]. **daily-arXiv-ai-enhanced** (about 3k stars, pushed 2026-09-08) crawls chosen arXiv categories daily in GitHub Actions, summarises with a configurable LLM, publishes to GitHub Pages, and adds plug-in interest filters, for about 0.2 CNY a day [43]. **ArxivDigest** (MIT, about 470 stars, dormant since 2024-05) ranks arXiv papers against a natural-language interest description with an LLM [44]. **n8n** hosts many templates of the form schedule, then RSS read, then LLM summary with importance score, then Slack and Gmail [45]. **Kagi's Kite** (MIT, about 1.1k stars, pushed 2026-09-23) is an open news app from a search company [46]. A GitHub search for "news digest agent" and "arxiv digest" returns dozens of sub-100-star single-purpose projects (for example `al-strunova/ai-news-digest-agent`, `HarborYuan/paper_agent`) that repeat the same fetch-summarise-email shape.

**What the whole family lacks**, and what the package should add: (a) a declarative, versioned subject spec (they hard-code feeds and prompts); (b) persistent entity records that accumulate across runs, so "what's new" means a diff against known state rather than "the last 24 hours"; (c) cross-source deduplication at story level; (d) a feedback channel that changes future ranking; and (e) provenance and credibility grades on each claim. **Borrow:** GitHub-Actions-style cron as a zero-infrastructure scheduler, the importance score per item, and LLM-as-filter before LLM-as-writer (auto-news, n8n templates).

## 3. Methodology literature

### 3.1 Horizon scanning

The UK Government Office for Science *Futures Toolkit* treats horizon scanning as one of a dozen futures tools, feeding driver mapping (classifying forces for change, for example by PESTLE) and scenarios [47]; GO-Science also published a practical review of horizon-scanning approaches, tools and techniques [48]. The OECD describes horizon scanning as "a systematic exploratory method" for detecting weak signals that are then analysed for relevance, trajectory and implications, and notes that web scraping, LLMs and machine-learning data mining now complement expert scanning [49]; its 2026 report focuses specifically on building capacity in *technology* horizon scanning [50]. The EU Policy Lab and JRC run horizon scanning in phases from signal scanning, to validation and prioritisation, to sense-making, and in workshops narrow about 20 weak signals down to the three most impactful, published as newsletters [51], [52]; the JRC has also used bottom-up text mining of Scopus keywords to find weak signals in science and technology [53]. Cuhls warns that horizon scanning is "only a part of the game": it identifies "things to come", can be automated as a stand-alone activity, but is not debate or strategy building, and over-trust in automated prediction is a real risk [54]. Schmidt et al. (2025) built open-source Python tools for horizon scans (SCANAR for news retrieval with deduplication and unsupervised relevance ranking; AIDOC for semantic re-ranking) and report about 62% less manual screening at 95% recall [55].

### 3.2 Technology and competitive intelligence

Lichtenthaler's study of 26 multinationals found that technology intelligence is coordinated through hierarchical, hybrid and informal structures at once, never structurally alone [56]. Herring's *Key Intelligence Topics* (KITs) process derives intelligence needs from interviews with decision-makers and sorts them into three categories: strategic decisions and actions, early-warning topics, and descriptions of key players [57]. SCIP, founded in 1986, is the professional body for competitive intelligence [58]. **Lesson:** a subject spec should begin with the *decision or question* it serves (a KIT), not with keywords; and the three KIT categories map naturally onto three spec kinds: decision support, early warning, and actor profiles.

### 3.3 Weak signals

Ansoff (1975) introduced weak signals to address two failures of strategic planning: strategic information arrives too late for effective response, and the planning cycle is too slow for fast-moving events; he argues for acting on vague, early indicators rather than waiting for strong ones [59]. Hiltunen (2008) replaces "weak signal" with the *future sign*, which has three dimensions: the **signal** (number and visibility of observations), the **issue** (the underlying change and how widely it diffuses), and the **interpretation** (what the receiver takes it to mean) [60]. Yoon (2012) operationalised this for text: *degree of visibility* (term frequency) and *degree of diffusion* (document frequency) are tracked with time-weighted growth rates on a Keyword Emergence Map and a Keyword Issue Map; weak signals are terms with low frequency but high growth [61], [62]. BERTrend (2024) moves the same idea to neural topic models in an online setting, classifying topics into noise, weak signals and strong signals from document counts and update frequency [63]. **Lesson:** store signal, issue and interpretation as separate fields, and compute visibility, diffusion and growth per entity so "emerging" is a measured property, not an LLM's impression.

### 3.4 The French *veille* and *intelligence économique* tradition

The 1994 Martre report, *Intelligence économique et stratégie des entreprises*, is regarded as the founding text of French economic intelligence and stresses that it is inseparable from networks [64]. AFNOR's experimental standard **XP X50-053** (April 1998), *Prestations de veille et prestations de mise en place d'un système de veille*, covers watch services on the technological, commercial, economic, competitive, legal and regulatory environment, whether internal or external, and defines shared terminology, roles and commitments between client and provider, the process, and the required competencies [65]. **Lesson:** the standard frames veille as a *service with a client*, which argues for recording, per subject, who the digest is for, what commitments (cadence, coverage) it carries, and whether they were met.

### 3.5 Intelligence cycle, source grading and maturity models

The intelligence cycle runs direction (planning), collection, processing, analysis, dissemination and feedback, with fluid movement back to earlier stages [66]. The **Admiralty code** (NATO 6x6) grades each item on two independent axes: source reliability A to F (A completely reliable; B usually reliable; C fairly reliable; D not usually reliable; E unreliable; F cannot be judged) and information credibility 1 to 6 (1 confirmed by independent sources; 2 probably true; 3 possibly true; 4 doubtful; 5 improbable; 6 cannot be judged), giving grades such as B2 [67]; it is widely used in cyber threat intelligence [68]. Gartner's **Hype Cycle** places technologies on five phases: Innovation Trigger, Peak of Inflated Expectations, Trough of Disillusionment, Slope of Enlightenment and Plateau of Productivity [69]. NASA's **Technology Readiness Levels** grade maturity from TRL 1 (basic principles) to TRL 9 (proven in operation) [70]. **Lesson:** these are orthogonal axes (how much we trust *this report*; how mature *this technology* is; how excited *the market* is; what *we* recommend) and conflating them is the commonest modelling error in radar tools.

## Design lessons for the package

1. **Spec files are KITs, not keyword lists.** Each subject spec should state the question or decision it serves and its kind (decision support, early warning, actor profile) [57], its audience and service commitments (cadence, coverage) in the spirit of XP X50-053 [65], then sources, queries, and a small *exemplar set* of known-relevant items that works better than keywords for relevance scoring [29], [30], [31].
2. **Entity record fields.** Identity (`id`, `name`, `aliases`, `kind`: technology, organisation, person, paper, product, standard); `subjects` (which specs track it); `quadrant` and `ring` with a `ring_history` of dated moves and a derived `movement` (new, in, out, unchanged) [16], [17], [18]; `maturity` (TRL-like) and `hype_phase`, kept separate from the ring [69], [70]; `signal` metrics (visibility, diffusion, growth, first and last seen) [61], [63]; `interpretation` (our current reading, with author and date) kept separate from observations [60]; `observations` (links to evidence items); `events` of typed kinds (release, funding, acquisition, leadership change, paper, benchmark) [3], [27]; `feedback` (likes, mutes, ratings) [13], [31]; and `last_reviewed` so silence can be detected.
3. **Every evidence item carries an Admiralty grade.** Source reliability (A to F) is a property of the *source* record, learned and editable; information credibility (1 to 6) is a property of the *item*, raised by independent corroboration across sources [67]. Defaulting both to F and 6 is honest and still useful. Digests should show the grade next to each claim.
4. **Radar semantics with a fade rule.** Adopt the four rings with Thoughtworks' 2026 naming (Adopt, Trial, Assess, Caution) as the default, configurable per subject, and borrow the rule that an entity which does not move fades from the digest after one edition unless something new happened [15], [16]. Export BYOR/Zalando JSON so any subject renders as a radar for free [17], [18].
5. **Close the cycle.** Model the full intelligence cycle as explicit stages (direction = spec, collection = source adapters, processing = normalise, dedup and match, analysis = entity update and signal scoring, dissemination = digest and Q&A, feedback = ratings and mutes) and make feedback change the next run's ranking [66], [54]. Mute is a first-class negative signal, not a delete [4], [13].
6. **Signal versus noise is measured, then interpreted.** Compute per-entity visibility, diffusion and growth over time windows (Yoon's maps; BERTrend's noise/weak/strong classes) before any LLM writes a sentence; use the LLM for filtering and interpretation, with citations to the graded evidence [61], [63], [34], [40].
7. **"What's new" is a diff against stored state.** Unlike every digest pipeline surveyed [38], [40], [42], [43], persist entity records and answer "what's new since T" as the set of changed fields and new observations, which also makes digests idempotent and cheap.
8. **Source seams worth having in v1.** RSS/Atom via `reader` [14]; page-watch via selectors, in the manner of changedetection.io [8]; GDELT DOC for global news [20], [22]; Google/Talkwalker alert feeds as zero-code query sources [23], [25]; arXiv, Hugging Face Daily Papers and Semantic Scholar for research [33], [29]; notifications through a single dispatch seam (Apprise-style) [8].
9. **Do not over-automate the judgement.** Cuhls and the EU Policy Lab both keep a human sense-making and prioritisation step after scanning [54], [51]; the package should propose ring moves and interpretations as reviewable suggestions, never apply them silently.
10. **Own the data.** Keep everything in plain key-value stores on local disk so the archive survives any upstream project's demise, as TT-RSS users learned in 2025 [11].
